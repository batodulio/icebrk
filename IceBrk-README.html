The short version

A game library for hosts who want the room laughing in five minutes.

IceBrk is a web platform for customizable icebreaker and party games, made for corporate events, schools, and everyday gatherings. Hosts pick a game, tune it to their group in a few minutes, and run it live — the timing, scoring, and celebration all live in the same screen.

Make it yours

Run it live

Project the Play Arena, hit start, and let the confetti, sound cues, and scorekeeping carry the energy.

Component inventory

Every layer, named.

The full list of what IceBrk runs on today, grouped from infrastructure up to the screen.

1 · Local development

  • Node + npm — workspace tooling and lockfile-pinned installs
  • Vite 6 dev server with hot module replacement (npm run dev)
  • @vitejs/plugin-react — Fast Refresh for React components
  • TypeScript 6 — npm run typecheck via tsc --noEmit
  • ESLint 9 with react-hooks and react-refresh plugins
  • .env.local — Supabase URL and anon key, kept out of git

2 · Source control & CI/CD

  • GitHub — batodulio/icebrk, the single source of truth
  • Branches — main for production, dev for active work, test for trials
  • Vercel Git integration — every push builds and deploys automatically
  • Preview deploys — each branch and PR gets its own live URL
  • Versioned alongside the code — supabase/schema.sql, the branding guide, the branding skill, and the README
  • Room to grow — GitHub Actions can layer on lint and typecheck gates when the team expands

3 · Build & hosting

  • Vercel Build — npm install then vite build using the auto-detected Vite preset
  • Output — a static bundle: index.html plus content-hashed JS and CSS
  • Build-time env injection — VITE_SUPABASE_URL and VITE_SUPABASE_ANON_KEY land in the bundle
  • Vercel Edge Network — global CDN delivery with HTTPS and automatic certificates
  • Static SPA — one HTML entry point, routing handled in the browser

4 · Client application

  • React 19 with StrictMode
  • react-router-dom 7 — BrowserRouter over /, /:gameId, /login, /support, /suggest-a-game
  • AuthProvider — app-wide context over the Supabase session
  • Landing page — Nav, Hero, ValueProps, GameLibrary, HowItWorks, Celebrate, Quote, FinalCta, Footer
  • GameShell — shared chrome, header, and tab strip for all six modules
  • Shared kit — gameCatalog, themes, participants, RosterEditor, UtilitySelect, ConfettiBurst, sound.ts
  • Plain CSS — index.css and games.css with brand tokens as custom properties

5 · State & persistence

  • sessionStore — module-level Map holding live objects; state survives moving between games and resets on a full refresh
  • useCloudSync — loads the host's saved row once, then autosaves every change with a 900 ms debounce
  • Unmount flush — a pending edit writes on the way out, so quick navigation keeps the change
  • Graceful fallback — builds that skip Supabase config keep full session-local play
  • localStorage — supabase-js keeps the auth session there across refreshes

6 · Data & identity (Supabase)

  • Supabase Auth — username plus password, mapped to a synthetic internal address, with email confirmation switched off
  • PostgREST — the browser calls the data API directly with the anon key and the signed-in user's JWT
  • Postgres — six *_settings tables, one unique row per host per game
  • jsonb columns — rosters, questions, boards, cards, and items stored in the exact shape the app already uses
  • Row Level Security — enabled on every table, with select / insert / update / delete policies scoped to auth.uid()
  • Triggers — set_updated_at() keeps updated_at fresh on every write
Data model

Six tables, one shape.

Every table carries id, a unique user_id referencing auth.users with cascade delete, theme_id, created_at, and updated_at. The columns below are what each game adds on top.

would_you_rather_settingsquestions jsonb · timer_secondsPaired A/B prompts, round timer up to 90 seconds
jeopardy_settingsboard jsonb · teams jsonbCategories with point-valued clues, plus team names and scores

Request flow

What happens when a host saves a board.

The host types in the Customize tab

React state updates immediately and the Customize surface re-renders, so editing stays instant.

sessionStore keeps the value in memory

Navigating to the library and back returns the host to the same board.

useCloudSync starts a 900 ms debounce

Rapid keystrokes collapse into a single write instead of one request per character.

supabase-js upserts on user_id

An HTTPS call to PostgREST carries the anon key plus the signed-in host's JWT.

Row Level Security checks the claim

Postgres compares auth.uid() to user_id and applies the write to that host's row alone; the trigger stamps updated_at.

Next login loads it back

On mount the hook selects the saved row once and hands it to the game module before autosave resumes, keeping stored setups intact.

Configuration

What it takes to run this.

Environment variables

  • VITE_SUPABASE_URL — project URL from Supabase → Settings → API
  • VITE_SUPABASE_ANON_KEY — public anon key, safe in the browser because RLS guards every table
  • Set locally in .env.local and in the Vercel project settings for deployed builds

Supabase setup

  • Run supabase/schema.sql once in the SQL Editor to create tables, triggers, and policies
  • Authentication → Providers → Email: leave "Confirm email" switched off, since signup uses a synthetic internal address
  • Keep the service role key on the server side only — the app runs entirely on the anon key

Local commands

  • npm install — restore dependencies from the lockfile
  • npm run dev — Vite dev server with hot reload
  • npm run build — production bundle, same command Vercel runs
  • npm run preview — serve the built bundle locally
  • npm run lint · npm run typecheck — quality gates before a push

Deploy path

  • Work on dev, review the preview URL Vercel posts back
  • Merge to main to promote the same build to production
  • Schema changes ship as SQL applied in the Supabase dashboard, versioned in the repo

Pick Static Web Apps when…

  • A branded domain on HTTPS matters at $0 — this is the single biggest difference
  • You want PR preview URLs as part of the review habit
  • Hosts are spread out and edge delivery is worth having
  • Sign-in through GitHub or a Microsoft account is acceptable for now

Pick App Service when…

  • You want branded email-and-password sign-in on the free tier — Easy Auth with Entra External ID delivers exactly that
  • A single Express codebase is easier for you to reason about than static plus functions
  • Passwordless database access through managed identity appeals
  • You expect server-side work that outgrows HTTP-triggered functions
  • icebrk.azurewebsites.net is fine for now, or the ~$9.49/mo Shared tier is acceptable later
Recommendation for IceBrk. Static Web Apps, because a party-game link gets pasted into group chats and a free branded domain on HTTPS is worth more here than a long-lived server. If the username-and-password sign-up is the part you refuse to give up, App Service flips the answer — Easy Auth clears the exact hurdle that costs $9/month on Static Web Apps. Either way the data layer below stays identical.

server.js — Express serves the SPA and the API from one process 
import express from 'express'
import path from 'node:path'
import sql from 'mssql'

const dist = path.resolve('dist')
const app = express()
app.use(express.json())

// Hashed filenames, so long cache lifetimes are safe. index:false keeps the
// SPA fallback below in charge of "/".
app.use(express.static(dist, { maxAge: '1y', index: false }))

// Passwordless: the App Service managed identity signs in to Azure SQL.
const pool = await new sql.ConnectionPool({
  server: 'sql-icebrk.database.windows.net',
  database: 'icebrk',
  authentication: { type: 'azure-active-directory-msi-app-service' },
  options: { encrypt: true },
}).connect()

const GAMES = new Set([
  'roulette', 'would-you-rather', 'jeopardy',
  'bingo', 'two-truths-and-a-lie', 'scavenger-hunt',
])

/** Easy Auth injects the same base64 client-principal header SWA uses. */
function callerId(req) {
  const header = req.get('x-ms-client-principal')
  if (!header) return null
  const principal = JSON.parse(Buffer.from(header, 'base64').toString('utf8'))
  return principal.userId ?? null
}

/** Hand the caller's id to SQL so the RLS policy can filter on it. */
async function scopedRequest(userId) {
  const request = pool.request()
  await request.input('uid', sql.NVarChar(128), userId)
    .query('EXEC sp_set_session_context @key = N\'user_id\', @value = @uid')
  return pool.request().input('uid', sql.NVarChar(128), userId)
}

app.get('/api/settings/:gameId', async (req, res) => {
  const userId = callerId(req)
  if (!userId) return res.sendStatus(401)
  if (!GAMES.has(req.params.gameId)) return res.sendStatus(404)

  const request = await scopedRequest(userId)
  const result = await request
    .input('gid', sql.VarChar(32), req.params.gameId)
    .query('SELECT payload FROM dbo.game_settings WHERE user_id = @uid AND game_id = @gid')

  const row = result.recordset[0]
  return row ? res.json(JSON.parse(row.payload)) : res.sendStatus(204)
})

app.put('/api/settings/:gameId', async (req, res) => {
  const userId = callerId(req)
  if (!userId) return res.sendStatus(401)
  if (!GAMES.has(req.params.gameId)) return res.sendStatus(404)

  const request = await scopedRequest(userId)
  await request
    .input('gid', sql.VarChar(32), req.params.gameId)
    .input('payload', sql.NVarChar(sql.MAX), JSON.stringify(req.body))
    .query(`MERGE dbo.game_settings AS target
            USING (SELECT @uid AS user_id, @gid AS game_id) AS source
              ON target.user_id = source.user_id AND target.game_id = source.game_id
            WHEN MATCHED THEN
              UPDATE SET payload = @payload, updated_at = sysutcdatetime()
            WHEN NOT MATCHED THEN
              INSERT (user_id, game_id, payload) VALUES (@uid, @gid, @payload);`)

  return res.sendStatus(204)
})

// Every other GET returns the shell, so /jeopardy and /support resolve.
app.get(/.*/, (_req, res) => res.sendFile(path.join(dist, 'index.html')))

app.listen(process.env.PORT || 8080)

Why OIDC rather than a publish profile. New App Service apps often ship with basic authentication switched off, and publish-profile deploys depend on it. A federated credential — App registration → Certificates & secrets → Federated credentials → GitHub Actions, scoped to batodulio/icebrk on main — works regardless, and leaves no long-lived secret in the repo. Give that identity the Website Contributor role on the resource group.
Two cold starts stack up here. An F1 app unloads after 20 minutes idle, and a serverless SQL database auto-pauses on its own schedule, so the first host of the evening can wait through both. Warming them costs the very quotas that keep this free — 60 CPU-minutes a day and 100,000 vCore-seconds a month — so the practical answer is to open the app a few minutes before the event starts, and to treat the Basic tier as the fix if that stops being acceptable.

Data layer

Azure SQL or Cosmos DB — both land at $0.

Six tables, one row per host per game, with the interesting parts already in jsonb. That shape fits either database, and the endpoint code barely differs between them. Pick on habits and on cold starts, since the allowances both clear IceBrk's needs comfortably.

🗄️ Azure SQL Database — free offer

  • 100,000 vCore-seconds, 32 GB data, 32 GB backup per database per month, for up to 10 databases per subscription
  • Row Level Security stays in the database, the closest match to what Supabase does today
  • T-SQL, the portal query editor, and every familiar tool from SSMS to the VS Code mssql extension
  • Pairs with App Service managed identity for passwordless access
  • Costs you a cold start: serverless auto-pause needs tens of seconds to resume

🌌 Cosmos DB for NoSQL — free tier

  • 1,000 RU/s and 25 GB free for the account lifetime, one account per subscription
  • The jsonb payloads land as documents exactly as they already exist
  • Stays warm — a point read answers in single-digit milliseconds any time of day
  • Access rules live in the endpoint rather than the database
  • Fits either host; it is what option 1 above assumes

The document shape (Cosmos)

container: settings — one item per host per game 
{
  "id": "roulette",                   // gameId — unique within the partition
  "userId": "aad|abc123...",          // partition key, from the client principal
  "gameId": "roulette",
  "participants": [ { "id": "…", "name": "Ana" } ],
  "spinSeconds": 5,
  "themeId": "colorful",
  "updatedAt": "2026-08-15T04:12:09.412Z"
}

Why this shape holds up

  • container.item(gameId, userId).read() is a point read — about 1 RU and single-digit milliseconds
  • An upsert of a document this size lands around 5–10 RU, so the 900 ms debounce keeps a busy host near 10 RU/s
  • 1,000 free RU/s therefore covers roughly 90 hosts customizing at the same moment
  • Storage per host is measured in kilobytes against a 25 GB allowance
  • Adding game #7 adds a field set, rather than a table and a migration

What the schema gives up

  • CHECK constraints move into the function (validate themeId and timer values before the upsert)
  • The set_updated_at() trigger becomes a line of JavaScript
  • Cascade delete on auth.users becomes a delete-by-partition call when a host closes their account
  • Row Level Security becomes the rule that the function only ever touches the caller's partition
  • Keep supabase/schema.sql in the repo as the record of what the data means

The relational shape (Azure SQL)

One table carries all six games, keyed on the caller and the game, with the payload as validated JSON. Security policies restore the Row Level Security guarantee that supabase/schema.sql relies on today.

db/schema.sql — Azure SQL equivalent 
CREATE TABLE dbo.game_settings (
  user_id     nvarchar(128) NOT NULL,
  game_id     varchar(32)   NOT NULL,
  payload     nvarchar(max) NOT NULL
    CONSTRAINT ck_game_settings_json CHECK (ISJSON(payload) = 1),
  updated_at  datetime2     NOT NULL
    CONSTRAINT df_game_settings_updated DEFAULT sysutcdatetime(),
  CONSTRAINT pk_game_settings PRIMARY KEY (user_id, game_id)
);

-- Row Level Security, driven by a per-connection session value
CREATE FUNCTION dbo.fn_rls_current_user(@user_id nvarchar(128))
RETURNS TABLE WITH SCHEMABINDING
AS RETURN
  SELECT 1 AS allowed
  WHERE @user_id = CAST(SESSION_CONTEXT(N'user_id') AS nvarchar(128));

CREATE SECURITY POLICY dbo.game_settings_rls
  ADD FILTER PREDICATE dbo.fn_rls_current_user(user_id) ON dbo.game_settings,
  ADD BLOCK PREDICATE  dbo.fn_rls_current_user(user_id) ON dbo.game_settings AFTER INSERT
  WITH (STATE = ON);

-- The function runs this right after opening the connection:
--   EXEC sp_set_session_context @key = N'user_id', @value = @callerId;
Budget the compute. 100,000 vCore-seconds is about 55 hours of active database time per month at the 0.5 vCore serverless floor, so auto-pause needs to stay on. Resuming a paused database takes tens of seconds, which a host feels — send a warm-up request when the app loads, and set a metric alert on Free amount remaining at 10,000 vCore-seconds. Cosmos sidesteps this entirely, which is why it leads this design.
API surface

Two endpoints replace PostgREST.

Everything useCloudSync does today is one read on mount and one debounced upsert. That maps to a single function with two methods.

api/src/functions/settings.js — Azure Functions v4, Node 22 
const { app } = require('@azure/functions')
const { CosmosClient } = require('@azure/cosmos')

const container = new CosmosClient(process.env.COSMOS_CONNECTION_STRING)
  .database('icebrk')
  .container('settings')

const GAMES = new Set([
  'roulette', 'would-you-rather', 'jeopardy',
  'bingo', 'two-truths-and-a-lie', 'scavenger-hunt',
])

/** Static Web Apps injects the signed-in user as a base64 JSON header. */
function callerId(request) {
  const header = request.headers.get('x-ms-client-principal')
  if (!header) return null
  const principal = JSON.parse(Buffer.from(header, 'base64').toString('utf8'))
  return principal.userId ?? null
}

app.http('settings', {
  methods: ['GET', 'PUT'],
  authLevel: 'anonymous',        // SWA route rules do the gating
  route: 'settings/{gameId}',
  handler: async (request, context) => {
    const userId = callerId(request)
    if (!userId) return { status: 401 }

    const gameId = request.params.gameId
    if (!GAMES.has(gameId)) return { status: 404 }

    if (request.method === 'GET') {
      try {
        const { resource } = await container.item(gameId, userId).read()
        return resource ? { jsonBody: resource } : { status: 204 }
      } catch (error) {
        if (error.code === 404) return { status: 204 }   // first visit
        context.error('read failed', error)
        return { status: 502 }
      }
    }

    const body = await request.json()
    await container.items.upsert({
      ...body,
      id: gameId,
      userId,                     // caller's partition, always
      gameId,
      updatedAt: new Date().toISOString(),
    })
    return { status: 204 }
  },
})

Client-side changes

  • src/lib/supabaseClient.ts retires; an apiClient.ts wraps fetch('/api/settings/…')
  • useCloudSync keeps its whole shape — load once, 900 ms debounce, flush on unmount — and swaps the two Supabase calls for fetch
  • AuthProvider reads /.auth/me instead of supabase.auth.getSession(), and exposes the same { user, loading, signOut }
  • AuthPage becomes provider buttons that link to /.auth/login/github (option A) or drives MSAL (option B)
  • src/lib/username.ts and the synthetic-address trick retire with option A
  • Same-origin /api means CORS stays out of the picture

Behaviour worth preserving

  • Guest play keeps working: a 401 from /api means "stay in session memory", the same branch that handles absent Supabase config today
  • The unmount flush can use navigator.sendBeacon when the page is closing, and plain fetch otherwise
  • Validate themeId and timer values in the function, since the CHECK constraints left with Postgres
  • Keep the debounce — it is what holds RU consumption flat

Provisioning runbook

Portal steps, in order.

Resource group

Create rg-icebrk-prod in Southeast Asia. Keeping one group makes the whole stack deletable in a single action.

Cosmos DB account

Azure Cosmos DB → Azure Cosmos DB for NoSQL → set Apply Free Tier Discount to Apply, and tick Limit total account throughput at 1,000 RU/s. The free discount is opt-in at creation only, and one account per subscription, so get this right on the first pass.

Database and container

Data Explorer → New Database icebrk with shared manual throughput of 1,000 RU/s → New Container settings, partition key /userId. A shared-throughput database holds up to 25 containers inside the free allowance.

Static Web App

Create → plan Free, source GitHub, authorize, then pick org / icebrk / main. Build presets → Custom: app location /, api location api, output location dist. On create it commits the workflow and adds the token secret for you.

Application settings

SWA → Settings → Environment variables → add COSMOS_CONNECTION_STRING for the Production environment. Preview environments carry their own settings, so add it there too when a PR needs live data.

Application Insights

SWA → Monitoring → Application Insights → turn it on. This is what makes managed-function logs visible at all.

Custom domain

SWA → Custom domains → add your hostname, prove it with the CNAME or TXT record at your registrar, and the managed certificate issues itself. Two domains are included; leave DNS hosted at the registrar to stay at $0.

Guardrail alerts

Cosmos → Metrics → alert on Total Request Units approaching the 1,000 RU/s cap. On Azure SQL, alert on Free amount remaining at 10,000 vCore-seconds. Application Insights → Usage and estimated costs → set a daily ingestion cap. All free to configure.

Taking the App Service path instead? Steps 1 and 6 through 8 carry over as written. Swap steps 2 through 5 for the two portal-settings cards under Option 2 above — Web App on F1 with a node server.js startup command and system-assigned identity on, then the free-offer database created through the Azure SQL hub with Allow Azure services switched on, and the CREATE USER … FROM EXTERNAL PROVIDER grant run once as the Entra admin.
Watch-outs

Things that bite on the way through.

Platform limits

  • Managed Functions support HTTP triggers only, and managed identity plus Key Vault references arrive with bring-your-own Functions — so the Cosmos key lives in app settings and gets rotated there
  • SLA coverage begins on the Standard plan, which suits this stage and is worth a conscious nod
  • 100 GB/month is where the Free plan stops; Standard adds overage at $0.20/GB, ideally arranged ahead of the traffic
  • Custom auth provider registration is a Standard-plan feature, which is what shapes the auth decision above
  • Cosmos free tier is one account per subscription and opt-in at creation; changing your mind means a new account
  • Azure SQL free databases lock to one region per subscription after the first one, and the auto-pause option caps the database at 4 vCores with 7-day point-in-time restore
  • App Service F1 keeps you on *.azurewebsites.net — a custom domain begins at Shared (D1) and a TLS binding for it at Basic (B1)
  • F1 gives 60 CPU-minutes a day and unloads the app after 20 minutes idle, since Always On begins at Basic
  • Free and Shared App Service tiers stay on a single shared instance, so scale-out and deployment slots arrive with higher tiers

Build and runtime

  • Set apiRuntime explicitly — Node 18 and older are past their support dates, Node 20 and 22 are current
  • Private repos draw from 2,000 Linux minutes a month, and Windows runners count double while macOS counts tenfold — stay on ubuntu-latest
  • Preview environments cap at 3; the close_preview job returns slots as PRs merge
  • Run swa start from the SWA CLI locally to emulate /api and the auth headers, rather than discovering behaviour differences in CI
  • Application Insights only shows function logs once it is switched on for the app
  • Deployment tokens are long-lived — rotate on the SWA overview blade if one ever leaks
