The short version

A game library for hosts who want the room laughing in five minutes.

IceBrk is a web platform for customizable icebreaker and party games, made for corporate events, schools, and everyday gatherings. Hosts pick a game, tune it to their group in a few minutes, and run it live — the timing, scoring, and celebration all live in the same screen.

Pick a game

Six ready-to-run games in the library today, each with its own play surface and rhythm.

Make it yours

Type in your own questions, names, prompts, and board categories. Choose a color theme and a timer that fits the room.

Run it live

Project the Play Arena, hit start, and let the confetti, sound cues, and scorekeeping carry the energy.

End-to-end architecture

From a laptop commit to a room full of players.

Everything running in production today, in order: source control, continuous delivery, hosting, the browser app, and the managed data layer behind it. One Node process serves the site and the API, reaching the database through an identity Azure manages, which keeps the whole stack free of stored credentials.

Live on Azure, entirely on always-free tiers — $0/month. Hosting moved here from Vercel + Supabase in August 2026. The reasoning, and what was considered instead, is in the What's next tab.

Component inventory

Every layer, named.

1 · Local development

  • Vite 6 dev server with hot module replacement (npm run dev) — runs the SPA exactly as a signed-out guest sees it
  • TypeScript 6 — npm run typecheck via tsc --noEmit
  • ESLint 9 flat config covering the React app and the Node host
  • npm start runs the real Express host against dist/
  • az login lets the same code reach the live database locally, because the connection uses azure-active-directory-default

2 · Source control & CI/CD

  • GitHub — batodulio/icebrk, deploys from main
  • GitHub Actions — .github/workflows/azure-app-service.yml
  • Gates — lint and typecheck run before any deploy, so only a passing build reaches Azure
  • OIDC federated credential on app registration gh-icebrk-deploy, scoped to repo:batodulio/icebrk:ref:refs/heads/main
  • Preflight steps report whether each secret resolved and the exact subject GitHub asserts — printing booleans in place of values
  • Role — Website Contributor on the resource group, rather than subscription-wide Contributor

3 · Hosting

  • Azure App Service icebrk-app — F1 Free, Linux, Node 22, Southeast Asia
  • Startup command node server.js
  • Deployed artefact — the repo with dist/ built and dev dependencies pruned
  • App settings — SQL_SERVER and SQL_DATABASE, addressing only
  • Free-tier shape — 60 CPU-minutes/day, single shared instance, app unloads after 20 minutes idle

4 · The Express host (server.js)

  • Static — express.static(dist) with a one-year cache, safe because Vite emits hashed filenames
  • API — GET and PUT /api/settings/:gameId
  • SPA fallback — every other GET returns index.html, so /jeopardy resolves
  • Unknown /api paths 404 rather than returning the HTML shell
  • Security headers — CSP, HSTS, nosniff, frame-ancestors none, and a suppressed x-powered-by
  • Rate limit — 120 requests/minute per caller, protecting the daily CPU and monthly vCore budgets

5 · Client state & sync

  • sessionStore — module-level Map; state survives moving between games and resets on a full refresh
  • useCloudSync — loads the saved row once, then autosaves every change with a 900 ms debounce
  • Unmount flush — a pending edit is written with keepalive so quick navigation keeps it
  • Guest play — a 401 from /api means "stay in session memory", so signed-out hosts keep the full experience
  • authClient — reads /.auth/me, handling both the App Service and Static Web Apps response shapes

6 · Data & identity

  • Easy Auth — Microsoft provider handles the credentials, so they stay outside the app
  • Managed identity — the app's own Azure identity signs in to SQL, leaving every credential out of the codebase
  • Azure SQL icebrk-test — free offer, serverless with auto-pause, Entra-only authentication
  • One table — dbo.game_settings, keyed on (user_id, game_id), payload validated by an ISJSON constraint
  • Row Level Security — filter and block predicates over SESSION_CONTEXT
  • Schema of record — db/azure-sql-schema.sql
Data model

One table, six games.

What used to be six Postgres tables with jsonb columns is a single table keyed on the caller and the game, with the game's own settings stored as validated JSON.

db/azure-sql-schema.sql 
CREATE TABLE dbo.game_settings (
  user_id     nvarchar(128) NOT NULL,   -- Easy Auth principal id (stable object id)
  game_id     varchar(32)   NOT NULL,   -- roulette | jeopardy | bingo | ...
  payload     nvarchar(max) NOT NULL
    CONSTRAINT ck_game_settings_json CHECK (ISJSON(payload) = 1),
  updated_at  datetime2     NOT NULL
    CONSTRAINT df_game_settings_updated DEFAULT sysutcdatetime(),
  CONSTRAINT pk_game_settings PRIMARY KEY (user_id, game_id)
);

-- Visible only to the identity the connection declared for itself
CREATE FUNCTION dbo.fn_rls_current_user(@user_id nvarchar(128))
RETURNS TABLE WITH SCHEMABINDING
AS RETURN SELECT 1 AS allowed
WHERE @user_id = CAST(SESSION_CONTEXT(N'user_id') AS nvarchar(128));

CREATE SECURITY POLICY dbo.game_settings_rls
  ADD FILTER PREDICATE dbo.fn_rls_current_user(user_id) ON dbo.game_settings,
  ADD BLOCK PREDICATE  dbo.fn_rls_current_user(user_id) ON dbo.game_settings AFTER INSERT
  WITH (STATE = ON);
Row Level Security applies to administrators too. A plain SELECT in the portal query editor returns an empty result, because the session has yet to declare an identity — which looks like missing data and is not. Adopt an identity with sp_set_session_context first, or lift the policy briefly and put it back.
Request flow

What happens when a host saves a board.

The host types in the Customize tab

React state updates immediately and the surface re-renders, so editing stays instant.

sessionStore keeps the value in memory

Navigating to the library and back returns the host to the same board, signed in or not.

useCloudSync starts a 900 ms debounce

Rapid keystrokes collapse into a single write instead of one request per character.

The browser PUTs to /api/settings/:gameId

Same origin, so the Easy Auth session cookie travels with it automatically.

Express resolves the caller

It reads x-ms-client-principal-id, a header the platform strips from inbound requests and re-injects itself — so a browser is unable to forge one. Identity comes from the header alone, leaving the request body out of it.

One batch sets the identity and writes

sp_set_session_context and the MERGE run together, guaranteeing the same pooled connection so the security predicate sees the right host. Splitting them across two calls would risk applying one host's identity to another's connection.

Row Level Security has the final word

Postgres-style isolation, enforced in the database: the block predicate refuses a row stamped with anyone else's id, whatever the application layer believes.

The stack in one line

Push to main → GitHub Actions builds and signs in with OIDC → Azure App Service F1 runs one Express process behind Easy Auth → managed identity reaches Azure SQL, where Row Level Security scopes every row to the host who made it. Every credential in that chain is issued and rotated by Azure.

Decision record

Why it looks like this.

App Service over Static Web Apps

  • Static Web Apps offers 2 free custom domains and PR preview environments — genuinely better on both counts
  • But registering a custom auth provider there requires the Standard plan at about $9/month
  • App Service Easy Auth accepts any OIDC provider on the free tier, which keeps branded email-and-password sign-up reachable at $0
  • Preserving that path mattered more than the domain, so App Service won
  • The cost is real: the custom domain waits for a paid tier, and a cold start follows 20 minutes idle

Azure SQL over Cosmos DB

  • Cosmos free tier stays warm and matches the old jsonb documents exactly — the tidier technical fit
  • Azure SQL keeps Row Level Security in the database, closest to what the Postgres policies did
  • T-SQL and the portal query editor were the more familiar tools for this team
  • The cost is auto-pause: the first query after idle takes tens of seconds
  • Cosmos remains a clean swap if cold starts ever become the thing that hurts

Managed identity over a connection string

  • The database trusts an identity Azure rotates internally, so nothing needs storing or rotating by hand
  • App settings carry addressing only — SQL_SERVER and SQL_DATABASE are safe in a screenshot
  • The server is set to Entra-only authentication, which removes the SQL admin password entirely
  • azure-active-directory-default means the same code works locally after az login

OIDC over a publish profile

  • A federated credential scoped to one repo and one branch replaces a long-lived deployment secret
  • Basic authentication stays switched off on the app, closing that path entirely
  • It cost a long debugging session to get right — the original app registration held a client ID Entra could not resolve, and every check short of the error message passed
  • Rebuilding the registration cleanly fixed it, and the workflow now prints its own diagnostics so the next failure explains itself
